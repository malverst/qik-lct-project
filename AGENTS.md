# AGENTS.md

## 1. Назначение

Этот файл — правила для AI-агентов, работающих над React Native проектом «Питомец Финни».

Главный источник требований — `PROJECT.md` и исходное ТЗ хакатона.

Если требование агента, идея разработчика или сторонняя рекомендация противоречит ТЗ, приоритет имеет ТЗ.

---

## 2. Команда

В проекте 2 человека:

### Участник 1
- генератор идей;
- дизайнер;
- отвечает за визуальную концепцию, UX/UI, игровые идеи и контентные решения.

### Участник 2
- генератор идей;
- разработчик;
- отвечает за архитектуру, React Native, игровую логику, хранение данных, тестирование и сборку.

AI-агент помогает команде, но не принимает продуктовые решения молча.

Если изменение заметно меняет игровую механику — сначала сформулировать предложение и причину, а не самовольно менять механику.

---

## 3. Стек

Использовать:
- React Native;
- Expo;
- TypeScript;
- AsyncStorage;
- локальный JSON/TS-контент.

Backend отсутствует.

Не добавлять сервер только потому, что это кажется «правильной архитектурой».

---

## 4. Архитектура

Предпочтительное разделение:

```text
src/
  app/
  components/
  features/
    pet/
    budget/
    purchases/
    savings/
    tasks/
    periods/
    progress/
    adult/
  domain/
    economy/
    pet/
    budget/
    period/
  content/
    tasks/
    purchases/
    goals/
    pet/
  storage/
  utils/
  types/
```

Конкретную структуру можно адаптировать к существующему Expo-проекту.

Правила:

- UI не должен содержать сложную финансовую логику.
- Расчёты бюджета находятся вне компонентов.
- Правила развития питомца находятся вне UI.
- Контент заданий находится отдельно от экранов.
- Слой хранения не должен быть размазан по компонентам.
- Типы доменной модели должны быть явными.
- Не использовать `any`, если можно описать тип.
- Не дублировать одну и ту же игровую формулу в разных местах.

---

## 5. Игровая логика

Игровая экономика должна быть детерминированной и тестируемой.

Любое изменение:
- баланса;
- накоплений;
- фактических расходов;
- состояния питомца;
- энергии;
- прогресса;
- стадии питомца

должно происходить через понятную доменную операцию.

Нельзя изменять баланс напрямую из UI.

Пример плохого подхода:

```ts
setCoins(coins - price)
```

в нескольких разных компонентах.

Предпочтительно:

```ts
purchaseItem(...)
```

через единый слой игровой логики.

---

## 6. План и факт

Критически важно не смешивать:

### План
Намерение ребёнка:
- обязательное;
- необязательное;
- накопления.

### Факт
Что реально произошло:
- покупки;
- фактические расходы;
- реально отложенные монеты.

План после подтверждения периода не должен незаметно изменяться из-за фактических покупок.

В конце периода производится сравнение.

---

## 7. Энергия и сон

Энергия — ограничитель количества действий/финансовых заданий за игровой сеанс.

Она нужна, чтобы ребёнок не прошёл весь контент за один раз.

Не использовать энергию как наказание.

Перед действием приложение должно понятно сообщать, если энергии недостаточно.

Сон/отдых восстанавливает энергию.

Не делать искусственное ожидание реального времени обязательным для демонстрационного режима.

---

## 8. Питомец

Один вид питомца — кот.

Кастомизация:
- цвет шерсти;
- кофточка;
- шляпа;
- украшение.

Минимум 9 комбинаций.

Стадии:
- малыш;
- подросток;
- взрослый.

Текущее состояние и стадия развития — разные понятия.

Не создавать механику, где ошибка ребёнка приводит к смерти, болезни или травме питомца.

---

## 9. Финансовые задания

Минимум 6 заданий и 3 темы:
- бюджет;
- накопления;
- покупки/платежи.

Задание должно требовать действия или принятия решения.

Обычный quiz с вопросом «выбери правильный ответ» сам по себе не подходит как основной формат.

Каждый результат должен иметь короткое объяснение.

---

## 10. Контент

Новые задания, товары и цели должны добавляться через данные.

Не писать:

```tsx
if (taskId === 1) ...
if (taskId === 2) ...
if (taskId === 3) ...
```

если то же самое можно выразить структурой данных.

Предпочитать:

```ts
const tasks = [...]
```

с типизированной моделью.

Контент должен быть отделён от компонентов.

---

## 11. UX для детей

Всегда проверять:

- понятна ли кнопка без длинной инструкции;
- короткий ли текст;
- достаточно ли крупная зона нажатия;
- понятно ли, почему изменился баланс;
- понятно ли, почему изменился питомец;
- понятно ли, что делать дальше.

Не использовать профессиональные финансовые термины без объяснения.

Не использовать стыд:

Плохо:
> «Ты неправильно распорядился деньгами».

Лучше:
> «Монет не хватило на обязательную покупку. Давай посмотрим, что можно изменить».

---

## 12. Ошибки пользователя

Ошибка должна становиться учебной ситуацией.

Допустимые способы восстановления:
- дополнительное задание;
- корректировка следующего плана;
- отказ от необязательной покупки;
- перенос желания.

Нельзя:
- удалять прогресс;
- резко наказывать ребёнка;
- делать питомца больным/умирающим;
- блокировать приложение из-за ошибки.

---

## 13. Локальные данные

Профиль хранится на устройстве.

После перезапуска должны сохраняться:
- профиль;
- питомец;
- баланс;
- покупки;
- накопления;
- цель;
- учебный прогресс;
- игровой период.

Storage-операции должны быть централизованы.

Не вызывать AsyncStorage хаотично из десятков компонентов.

---

## 14. Демонстрационный режим

Нужен тестовый профиль.

Он должен:
- начинаться с предсказуемого состояния;
- позволять пройти 5 периодов;
- не требовать ожидания реального времени;
- сбрасываться в исходное состояние.

Не строить демонстрацию на ручном редактировании данных через код.

---

## 15. UI и дизайн

Стиль:

> мультяшный кот + современный минималистичный интерфейс.

Предпочтения:
- светлый интерфейс;
- чистые карточки;
- скругления;
- аккуратные анимации;
- понятная типографика;
- дружелюбная графика;
- отсутствие визуального шума.

Не добавлять тяжёлые UI-библиотеки без причины.

---

## 16. Тестирование

Обязательно тестировать:

### Экономику
- покупка при достаточном балансе;
- покупка при недостаточном балансе;
- невозможность отрицательного баланса;
- план не превышает бюджет;
- накопления;
- снятие накоплений;
- сравнение плана и факта.

### Игровой цикл
- завершение периода;
- переход к следующему;
- изменение стадии питомца;
- восстановление после ошибки.

### Storage
- сохранение;
- перезапуск;
- сброс профиля.

---

## 17. Git

Коммиты должны быть небольшими и логичными.

Примеры:

```text
feat: add pet creation flow
feat: add budget planning
feat: add savings goals
feat: add financial tasks
fix: prevent negative balance
test: add budget economy tests
```

Не смешивать в одном коммите:
- новую механику;
- полный редизайн;
- рефакторинг;
- исправление unrelated bug.

---

## 18. Перед изменением кода

Агент должен:

1. Изучить существующую структуру проекта.
2. Проверить package.json.
3. Проверить Expo-конфигурацию.
4. Найти существующие компоненты и навигацию.
5. Не создавать дубликаты уже существующей инфраструктуры.
6. Определить минимальный набор файлов для изменения.
7. После реализации проверить TypeScript/линтер/тесты, если они настроены.

---

## 19. Запрещено

Без явного решения команды нельзя:
- добавлять backend;
- добавлять регистрацию;
- добавлять аналитику с персональными данными;
- добавлять рекламу;
- добавлять реальные платежи;
- добавлять социальную сеть;
- менять основную механику бюджета;
- убирать обязательные функции ТЗ;
- заменять локальное хранение сервером;
- делать обязательный интернет;
- использовать AI ради галочки;
- добавлять зависимости без необходимости.

Перед завершением задачи агент проверяет:

- [ ] соответствует PROJECT.md;
- [ ] не нарушает ТЗ;
- [ ] TypeScript без новых ошибок;
- [ ] нет лишних зависимостей;
- [ ] нет секретов;
- [ ] состояние сохраняется;
- [ ] ошибка пользователя обработана;
- [ ] UX понятен ребёнку 7–11 лет;
- [ ] обязательный сценарий не сломан.
